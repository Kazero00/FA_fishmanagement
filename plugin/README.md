# FantasyAquariumMod — 使用说明

给 **Fantasy Aquarium**（Steam appid 3183350，Unity 2022.3.54f1 / Mono x64）加的功能。

## 一、当前状态：已经装好了

| 项目 | 位置 |
|---|---|
| BepInEx 5.4.23.2 (win x64) | 游戏根目录：`winhttp.dll`、`doorstop_config.ini`、`.doorstop_version`、`changelog.txt`、`BepInEx\` |
| 插件 | `BepInEx\plugins\FantasyAquariumMod.dll` |
| 插件源码 | `~/fantasy_aqua/plugin/FantasyAquariumMod/`（workspace） |

**直接启动游戏就生效**，不需要加启动参数。首次运行后生成配置 `BepInEx\config\local.fantasyaquarium.mod.cfg`。

---

## 二、功能 1：跨鱼缸鱼类管理（F10）

原版只能在**单个鱼缸**里一条条点鱼。这个面板把所有鱼缸的鱼汇总成一张表。

### 筛选（所有条件**可任意叠加**）

| 维度 | 取值 |
|---|---|
| 鱼缸 | 全部 / 各缸（按钮上带该缸剩余空位） |
| 异色 | 全部 / 普通 / **异色**（= 游戏里的 `FishType.Colorful`，官方 UI 叫「异色」；与稀有度**正交、可叠加**） |
| 稀有度 | 全部 / **绿色 / 蓝色 / 金色 / 闪彩 / 闪彩★** —— **可多选**（点一下切换）。官方把 rarity 3 与 4 都叫「闪彩」，但两者**获取渠道完全不同**（见附录），所以这里把 rarity 4 标为 **闪彩★** 并单独可筛 |
| 锁定状态 | 全部 / 已锁 / 未锁 |
| 收益/天 | 手动输入最小~最大 |
| 售价 | 手动输入最小~最大 |
| **养成值** | 手动输入最小~最大（= 长成大只所需总经验 `experienceAll`，越小越快养大） |
| 成长 | 全部 / **成年**（成长度已满 100%）/ **幼年**（未满）—— 按钮切换 |

- **收益 / 售价 / 养成值**三个数值区间**可只填一边**（只填最小 = ≥X，只填最大 = ≤X，都留空 = 不限），**回车即应用**（也点「应用」）；点「清除」清空。
- 边打字不会重建列表，所以不会丢焦点/光标。
- 顶部实时显示当前生效的全部条件，例如：`筛选：缸03 + 异色 + 稀有金色 + 收益≥200 → 命中 7/706 条`。
- 条件变化时，卖出按钮的「二次确认」状态会自动取消，换条件后不会误触第二击。

### 排序
`稀有度↓` / `收益↓` / `售价↓` / `成长↓` / `按鱼缸` / `按编号`

### 批量操作（两组，语义分开）

| 作用对象 | 操作 | 按钮 |
|---|---|---|
| **整个筛选结果**（跨页全部命中） | 加锁 / 解锁 / 卖出 | `加锁筛选 (N)` / `解锁筛选 (N)` / `卖出筛选 (N)` |
| **勾选的行** | 加锁 / 解锁 / 卖出 / 换缸 | `加锁选中 (N)` / `解锁选中 (N)` / `卖出选中 (N)` / `换缸到 00~NN` |

- 两个卖出都要**点两次确认**；锁定的鱼一律跳过，日志会说明实际处理条数。
- 换缸自动校验目标缸空位，放不下的跳过并在日志说明。
- 配合 `全选本页` 可以整页勾选。

### 单条与浏览
- 每行：`#ID 名称`（按稀有度着色）｜稀有｜体型｜异色｜鱼缸｜**养成值**｜收益/天｜售价｜成长% ｜`卖出` `锁定` `所在缸`
- 每页 14 条（9 个满缸约 700 条鱼也能翻）

> 典型用法 1（保护高收益）：收益最小填 `200` → 回车 → `加锁筛选 (N)`，所有收益 ≥200 的鱼一次性上锁。
> 典型用法 2（清理低收益）：缸选 05 + 类型普通 + 收益最大 `50` → 回车 → `卖出筛选 (N)`（两次确认）。
> 典型用法 3（只留能长的鱼）：成长点 `幼年` + 稀有度多选「绿色+蓝色」→ `加锁筛选` 或直接 `卖出筛选`。
> 典型用法 4（挑着搬缸）：筛选后逐条勾选 → `换缸到 03`。
> 典型用法 5（只留好养的）：养成值最大填 `14400`（≈4 小时就能养大）→ `卖出`/`加锁` 按需处理。

入口：右上角 **「鱼类管理 (F10)」** 按钮，或按 **F10**。

> 表头与数据行**共用同一份列定义**（见 `FishManagerPanel.Columns`），所以标签与数值严格对齐。

## 三、功能 2：购买时自动放进有空位的鱼缸

原版：当前鱼缸装不下就直接弹「鱼缸已满」，**完全买不了**。

现在：只要**所有鱼缸的空位加起来够**，就允许购买，并且每钓上来一条鱼都会自动落到：
1. 当前鱼缸（如果还有空位）；
2. 否则按鱼缸顺序找第一个有空位的缸。

细节：
- 数量选择器的 **「+」** 和 **「最大」** 也改成按总空位计算；
- 只有当**所有缸都放不下**时才会像原版一样提示「鱼缸已满」；
- 鱼被放进未激活（非当前）的鱼缸是安全的 —— 游戏自己加载存档时就是这么做的。
- 面板底部有 **`跨缸分流：开/关`** 按钮可随时切换本功能。

## 四、功能 3：抽奖机保留投资额

好感度投资幸运屋的 50 / 200 / 1000 投资票按钮，原版在**每次结算后会把次数清零**，
所以每抽一次都要重新点一遍（比如 10 次 1000 票 = 10000 金币档）。

现在：结算后**保留当前已选的投资额**，下次打开机器直接沿用，
并且把三档次数写进 BepInEx 配置，**跨游戏重启也保留**。

细节：
- 只改"待投资额的选择"，**不会自动结算/自动抽奖**，扣钱仍然由你点「结算」触发；
- 想清空：在机器里把次数减到 0（右键或「-」），或把配置里的 `SavedCount*` 改成 0；
- 配置项 `[Lottery] KeepInvestment = false` 可关闭本功能，恢复游戏原行为；
- 日志会打印 `[Lottery] 已保留投资额：按钮X ×N` / `[Lottery] 已恢复投资额：按钮X ×N`。

## 五、配置项

`BepInEx\config\local.fantasyaquarium.mod.cfg`：

```ini
[MultiTank]
## 购买时如果当前鱼缸放不下，自动把新鱼放进其它有空位的鱼缸（同时解除购买限制）。
AutoRedirectToOtherTanks = true

[FishManager]
## 是否显示“鱼类管理”入口按钮。
ShowFishManagerButton = true
## 打开/关闭鱼类管理面板的快捷键。
ToggleKey = F10
## 入口按钮横坐标，-1 表示贴右边缘。
ButtonX = -1
## 入口按钮纵坐标（左上角为 0）。
ButtonY = 120

[UI]
## false = 插件自建画布（1920x1080 坐标空间，默认）；true = 挂进游戏自己的画布下。
UseGameCanvas = false

[Growth]
## 非激活鱼缸里的鱼也按真实时间补算成长。
CatchUpInactiveTanks = true
## 补算间隔（秒，最小 10）。
CatchUpIntervalSec = 45

[Lottery]
## 抽奖机抽完后保留投资额（下次进入沿用，并写入配置跨重启保留）。
KeepInvestment = true
## 持久化的投资票次数（0-10），由插件自动写入。
SavedCount50 = 0
SavedCount200 = 0
SavedCount1000 = 0
```
改完重开游戏生效。（旧版本遗留的 `[AllTanksPanel]` 段已废弃，可整段删掉。）

## 八、已知限制

1. 面板由插件自建画布绘制，**美术风格和游戏原生 UI 不完全一致**（好处是零 prefab 依赖、游戏更新不易失效）。
2. 用面板切换鱼缸后，游戏原生 HUD（顶部鱼缸名/数值）不会立刻刷新，重新打开对应原生面板即同步。
3. 批量卖出**不可撤销**，所以做了二次确认；锁定的鱼不会被卖出。
4. 插件依赖游戏类名/方法名，游戏大版本更新后可能需要重新核对（用 ILSpy 看 `SaveLoadCntroller.Update`、`FishCard.InitFishToTank`、`FishBag.OnClickYes`、`UIGetFishOptionNumMoreEvent` 即可）。

## 附录：金币收益模型（反编译实证）

### 非当前鱼缸的"成长补算"（v0.8.12 定型）

游戏加载鱼缸的顺序是 `Instantiate(先触发 OnEnable) → LoadFish(后设真实数据)`，
所以**非当前鱼缸**里的鱼第一次 `OnEnable` 时 `falseTime` 还是空的，离线成长补算被跳过；
紧接着该缸就被 `SetActive(false)`，在玩家进入它之前不会再触发 `OnEnable` ——
这些鱼会一直停在存档里的成长值（典型现象：**大量鱼的成长度显示 0% 且长期不涨**）。
游戏自带的 `PeriodicTankRefresh` 每 600 秒才做一次类似的事，短会话根本撞不上。

打开 `[Growth] CatchUpInactiveTanks = true`（默认开）后，本 mod 每
`CatchUpIntervalSec`（默认 30 秒）对**非激活鱼缸**里的鱼做一次**纯数据层**补算：

    经验 += (现在 - falseTime) 的真实秒数      // 与游戏 OnEnable 时的补算公式一致
    falseTime = 现在                          // 锚点前移，绝不重复计入
    满上限则调用 FishToBig()

> ⚠️ v0.8.11 曾用"把一个非当前鱼缸激活 1 帧"的方式实现，会连带触发该鱼缸的水体/渲染组件，
> 导致运行中偶发**渲染黑屏**；v0.8.12 已彻底改为上面的纯数据计算，**不再触碰任何 GameObject**。

**核心公式**：一条鱼每 **86400 秒真实时间**产出 `fishInfo.moneyPerDay` 金币，**但只有成鱼才产出**。

```csharp
// FishMoneyAdder
_moneyPerFrame = fishMoneyPerDay / (86400f * 60f);      // 60fps 每帧
public void FishMoneyAdd() {
    if (_fish.GetIsBig())            MoneyController.Instance.EarnMoney(_moneyPerFrame);
    else if (_needExperienceFrame>0) _needExperienceFrame--;   // 没长成 → 先等(剩余成长×60)帧
    else                             MoneyController.Instance.EarnMoney(_moneyPerFrame);
}
```
* 在线：`MoneyListText.Update()` 每帧调 `MoneyController.InvokeAdder()`；
  delegate 里是**所有鱼缸**的鱼（不只当前显示的缸），每条鱼在 `Start()` 时注册。
* 离线：`TankManager.Save()` 把**所有缸里 `isBig` 的鱼**的 moneyPerDay 累加成 `offLineMoneyPerDay`；
  未成鱼把「剩余成长秒数 + moneyPerDay」存进 `smallOffLineMoneyList`；
  读档时 `RecalculateMoney()` 按经过秒数补发，**单次上限 1,000,000 金币**。
* 因此**在线与离线的速率完全相同**（都是 moneyPerDay/86400 每秒）——挂机不会有额外收益，
  唯一差别是单次读档最多补 100 万。

**推论**：面板里的「收益/天」列直接相加就是总收益/天；瓶颈只有两个——**槽位**（9 缸 × 80 = 720）与**成长度**。

| 稀有度 | 平均收益/天 | 满成长时间(中位) | 成鱼售价 | 回本天数(售价÷日收益) |
|---|---|---|---|---|
| 绿色 | 10.7 | 0.02 天 | 20 | 1.9 |
| 蓝色 | 30.9 | 0.17 天 | 86 | 2.8 |
| 金色 | 115.5 | 1.00 天 | 467 | 4.0 |
| 闪彩 | 253.6 | 2.00 天 | 1,636 | 6.4 |
| 闪彩★ | 328.8 | 0.12 天 | 1,003 | 3.1 |

> 结论：**卖了就没了永久收益**。只要打算继续玩超过上面那个"回本天数"，
> 成鱼就不该卖（除非为了给更高收益的鱼腾槽位）。

**只看金币（不考虑鱼）**：金币只由"非鱼类结果"发放——`LikabilityTicket.OnClickBtn()` 里
`if (result.Type == Fish) 弹鱼卡列表; else MoneyController.Instance.EarnMoney(result.Amount);`，
即**点开奖券时一次性进余额**。金币类结果只有 7 种：100 / 500 / 1000 / 3000 / 5000 / 10000 / 30000。
另外"3000 金币"同时是稀有鱼抽失败的补偿（r15/r16 80%、r17/r18 90%、r19 95% 降级到 `_result5`）；
恰投 50 与 ≥12500 这两档固定给鱼，**金币收益恒为 0**。

| 投入（左边界） | 出金币概率 | 期望金币 | 回报/投入 | 单次亏损概率 | 中位结果 |
|---|---|---|---|---|---|
| 50 | 0% | 0 | 0× | — | 鱼 |
| 100 | 20.6% | 87 | 0.87× | 79.4% | 鱼 |
| **1000** | **90.4%** | **1,031** | **1.03×（唯一为正）** | 90.4% | 100 金币 |
| 2000 | 80.3% | 1,985 | 0.99× | 80.3% | 500 金币 |
| 5000 | 44.6% | 3,588 | 0.72× | 91.7% | 鱼 |
| 10000 | 48.3% | 1,450 | 0.14× | 100% | 3,000 金币 |

> 投 1000 的均值虽为 +3%，但**单次亏损概率 90.4%**、标准差 4,342（每次期望净赚仅 +30.8），
> 要让波动小于期望收益约需 8 万次抽奖 —— 属于"需要巨额本金才收敛"的负偏态赌局，不是可行的赚钱手段。
> 若只为金币，**只投 1000，绝不投 2000 以上**。

## 附录：鱼的获取渠道（反编译实证）

全游戏只有**两条**会给鱼的路径：

### ① 商店鱼袋（普通抽卡）
`FishBag.OnClickYes` → `FishCardList.InitFishCardList(bagInfo, optionNum)` →
`DrawCard.InitFishPool()`。该池构建时**明确排除 rarity 4**：

```csharp
if (allFishInfo[i].rarity != 4) { fishPool.Add(...); }
```
所以普通渠道能出 绿色/蓝色/金色/闪彩（rarity 0–3），**永远出不了 rarity 4**。
异色则由 `DrawCard.IsColorfulFish()` 按概率决定，概率随**拥有家具数量**提升：
`rarity0: 0.8%×(1+k)`、`1: 6%×(0.5+k)`、`2: 7.5%×(1+k)`、`3: 20%×(0.5+k)`（k=拥有家具/总数）。

### ② 好感度投资幸运屋（唯一的 rarity 4 来源）
`LikabilityController.OnClickSettlementButton()` → `_allValue` = 本次结算投入总额 →
`DrawTicket()` 按区间选池 → `DrawFromPool()` 抽取 → `LikabilityTicket` →
`FishCardList.InitFishCardListLikability(resultList)`。

**区间是左闭右开**（`DrawTicket()` 里 `_allValue >= tuple.Item1 && _allValue < tuple.Item2`）：

| 条件（含边界） | 结果 |
|---|---|
| `_allValue == 50` | 固定 `_result1`（优先级最高，先于区间判断） |
| `51 ≤ x < 1000` | pool50to1000 |
| **`1000 ≤ x < 2000`** | pool1000to2000（**1000 属于这一档**） |
| `2000 ≤ x < 5000` | pool2000to5000（2000 属于这一档） |
| `5000 ≤ x < 10000` | pool5000to10000（5000 属于这一档） |
| **`10000 ≤ x < 12500`** | pool10000to12500（**10000 属于这一档**） |
| `x ≥ 12500` | 固定 `_result12`（金色异色×12，**不进池**） |

即：**左边界归本档，右边界归下一档**——1000/2000/5000/10000 都会拿到"更好"的那一档，不存在边界浪费。

投资票按钮：50 金币(+5 好感度) / 200(+25) / 1000(+150)，**每个按钮最多点 10 次**，
所以 `_allValue` 一定是 50 的倍数，且**上限恰好是 12500**（10+10+10 全满 = 直接触发保底，r4 概率归零）。
想刷 rarity 4 就点满 **10 次 1000 票 = 正好 10000**（落在最高档 2.78%，且不触发保底）。

**池大小与内容**（`LikabilityController.Start()` 逐条解析核对）：

| 单次投入 | 池大小 | 内容 |
|---|---|---|
| 恰为 50 | — | 固定 `_result1` = **4 条绿色异色**（不走池） |
| 51–1000 | **63** | r1×50（绿色异色×4）、r2×10（100 金币）、r3/r4/r5 各 1（500/1000/3000 金币） |
| 1000–2000 | **52** | r2×41（100 金币）+ 11 种各 1：500/1000/3000/5000/10000/30000 金币、绿色异色×12、蓝色异色×12、金色异色×4、金色异色×12、闪彩普通×4 |
| 2000–5000 | **33** | r3×20（500 金币）+ 13 种各 1：3000/5000/10000/30000 金币、绿异色×12、蓝异色×12、金异色×4、金异色×12、闪彩普通×4、闪彩异色×4、闪彩普通×12、闪彩异色×12、**闪彩★普通×4** |
| 5000–10000 | **12** | 30000 金币、绿异色×12、蓝异色×12、金异色×4、金异色×12、闪彩普通×4、闪彩异色×4、闪彩普通×12、闪彩异色×12、**闪彩★普通×4**、**闪彩★异色×4**、**闪彩★普通×12** |

1. **金币消耗**（`MoneyController.SpendMoney`，纯消耗）；
2. **好感度**（`SettlementAllButton()` 按你点了哪些票累加，与总额无关）：

   `LikabilityLevelReward()` 直接把结果塞给 `likabilityTicket.Init(...)`，

**实际概率与性价比**：

| 单次投入 | 出鱼 | 其中闪彩(r3) | 其中**闪彩★(r4)** | 平均每条 r4 鱼 |
|---|---|---|---|---|
| 51–1000 | 79.4% | 0% | **0%** | — |
| 1000–2000 | 9.6% | 1.9% | **0%** | — |
| 2000–5000 | 19.7% | 7.3% | **0.30%** | ≈28.9 万金币 |

> 结论：想刷 rarity 4，**单次投入控制在 5000–12499 之间**最划算；
> 凑到 ≥12500 反而被保底成 12 条金色异色，**一点 rarity 4 机会都没有**。
> 因为同区间内概率完全相同，**永远只投区间左边界**（1000 / 2000 / 5000 / 10000，可达值均为 50 的倍数）；
> 用 1000 金币票刷好感度（0.15/金币）把等级推到 4，可再白拿 2 批必定 r4 的奖励（4×闪彩★普通 + 4×闪彩★异色）。

其它细节：
* 闪彩(rarity 3) 的 `_result15/_result16` 在 `DrawFromPool` 里**有 80% 概率降级成 3000 金币**，所以"闪彩普通/异色"实际很难抽到；
* 好感度渠道里 **rarity 1/2 的鱼强制为异色**（代码直接写 `type = FishType.Colorful`）；
* 投资票：50 金币→+5 好感度、200→+25、1000→+150；
* 代码里有 `result.FishId == 64`（直接给「黑鲨」）的分支，但全代码无处给 `FishId` 赋值，属**遗留死代码**；
* 图鉴把 rarity 3 与 4 都算作「闪彩」（同一个 `UnlockedShiny` 计数），所以图鉴上看不出哪些是新闪彩——但 id ≥ 136 的那批（鱼娘/贝壳猫等 32 条）就是 rarity 4。
* 面板里 rarity 4 显示为 **`闪彩★`**（配色也更亮一档），并且筛选里 **`闪彩` 与 `闪彩★` 是两个独立可多选按钮**，方便只看"能靠投资抽到的那些"。

## 附录：为什么所有 UI 都写成「静态类 + Harmony 补丁驱动」

这是本项目最重要的踩坑结论，加任何新 UI/常驻逻辑都必须遵守：

- **本插件里，我们自己的 MonoBehaviour 收不到 Unity 的 `Update` / `OnGUI` / `LateUpdate` 回调** ——
  连 BepInEx 插件组件本身也一样（日志证明 `Plugin.Update()` 心跳一行都没有），
  但在 Chainloader 阶段创建的 GameObject 还会在场景加载完成时被销毁。
- **Harmony 补丁 100% 生效**（跨缸购买、鱼缸清单一直正常）。
- 因此：面板逻辑放在**静态类**里，由 `SaveLoadCntroller.Update` 的 **Harmony Postfix 每帧驱动**
  （该方法是场景常驻对象、每帧必跑，用于游戏自己的自动存档计时）；
  交互只用 UGUI `Button.onClick`（EventSystem 驱动，不需要 Update）。
